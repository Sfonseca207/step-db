# Decisiones de implementación

Registro de decisiones tomadas durante la implementación autónoma del MVP (SPEC §15.1). Formato: fecha · decisión · alternativa descartada · motivo.

| # | Fecha | Decisión | Alternativa descartada | Motivo |
|---|---|---|---|---|
| I1 | 2026-09-28 | Postgres 18 en Docker (`postgres:18`), volumen montado en `/var/lib/postgresql` y script `docker/initdb` que crea `stepdb_test`. | PGlite (plan B) | Docker respondió; no hizo falta el plan B. `DB_DRIVER` solo acepta `postgres` por ahora. |
| I2 | 2026-09-28 | El servidor corre con type stripping nativo de Node (v26) y carga `.env` con `--env-file-if-exists`. | `tsx`, `dotenv` | Node ≥ 24 lo soporta sin dependencias extra. |
| I3 | 2026-09-28 | `@dbml/core` 10.2 soporta propiedades personalizadas (`[step: "…"]`) y las expone en `field.metadata` / `table.metadata`. Se usa directamente. | Plan B con `note: '@step:…'` | Verificado empíricamente al empezar. |
| I4 | 2026-09-28 | Se añadió `tsconfig.server.json` (entorno Node, `moduleResolution: nodenext`) que incluye `server/` y `src/core/`. Los tests `*.test.ts` de `src/` se excluyen del proyecto de la app y se type-checkean en el del servidor. | Un solo tsconfig | `src/core` debe compilar en ambos entornos (DOM y Node). |
| I5 | 2026-09-28 | Las tablas sin schema (schema `public` de DBML) se identifican como `<defaultSqlSchema>.tabla` (p. ej. `dbo.venta`). | Mantener `public` | SQL Server usa `dbo`; la clave del layout y del diff queda coherente con el export. |
| I6 | 2026-09-28 | Las relaciones se normalizan con el lado "muchos" como `from` (`op` `>`); 1:1 y N:M conservan el orden declarado. Identidad: `from(cols)op to(cols)`. | Usar el orden de `endpoints` del parser | Las refs inline invierten el orden de los endpoints; normalizar da ids estables para el diff. |
| I7 | 2026-09-28 | Tipos Mongo de arreglo tipados: `"array<tipo>"` (entre comillas, porque DBML no acepta `<>` sin comillas) o `tipo[]`. | Sintaxis `array<tipo>` sin comillas | El parser de DBML la rechaza. |
| I8 | 2026-09-28 | Validaciones estructurales del core que bloquean el guardado: store (mongo solo en el archivo `mongo` y schema `mongo`), tipos Mongo permitidos, tabla duplicada y `[step: "…"]` con slug desconocido. | Solo advertencias | "Nunca se guarda un modelo que no parsea" (SPEC §4.2) se extiende a estas reglas estructurales. |
| I9 | 2026-09-28 | El prefijo visible de los tokens es `sdb_` + 8 caracteres (12 en total). | Primeros 8 caracteres (`sdb_` + 4) | Con 4 caracteres aleatorios es difícil distinguir tokens en la UI. |
| I10 | 2026-09-28 | Cada revisión guarda el contenido **nuevo** con su versión, el diff que lo produjo y un `summary` legible (columna extra). | Guardar el contenido anterior | Así el historial incluye la versión vigente, "restaurar" es escribir el contenido de una revisión y el log de actividad (RF-43) muestra el resumen sin recalcular. |
| I11 | 2026-09-28 | CSRF: además de `csrf()` de Hono (formularios), un guard rechaza métodos no seguros con `Origin` distinto a los orígenes de confianza o `Sec-Fetch-Site: cross-site`. Sin CORS (solo mismo origen). | Solo `csrf()` de Hono | `csrf()` solo revisa content-types de formulario; la API usa JSON. |
| I12 | 2026-09-28 | Fuera de producción, `http://localhost:$PORT` también es origen de confianza (para `npm start` local). | Solo `BETTER_AUTH_URL` | Permite probar el build servido por Hono sin cambiar `.env`. |
| I13 | 2026-09-28 | El slug de un step no cambia al renombrarlo, ni al reordenar. | Regenerar el slug | Las columnas `[step: "…"]` referencian el slug; cambiarlo rompería el modelo. |
| I14 | 2026-09-28 | Fuentes del sistema (sin Google Fonts). | Inter/JetBrains Mono por CDN | La CSP solo permite `font-src 'self'` y la app debe funcionar sin red externa. |
| I15 | 2026-09-28 | "Auto-organizar por step": ELK `layered` por cada step (vertical si tiene ≤ 4 tablas) y bloques en orden cronológico de izquierda a derecha, con salto de fila a ~2600 px. Sin agrupar: ELK `layered` sobre todo el modelo. La primera apertura sin layout usa el modo agrupado. | Nodos compuestos de ELK (`INCLUDE_CHILDREN`) | El modo jerárquico ordenaba los steps por dependencias y producía un diagrama muy ancho. |
| I16 | 2026-09-28 | Los marcadores crow's foot se dibujan dentro del componente de arista (no como `<marker>` SVG), con el color del step de cada extremo. El lado "1" es `0..1` si la FK admite nulos. | Marcadores SVG por color | Permite colorear cada extremo con su step (gradiente) sin depender de `context-stroke`. |
| I17 | 2026-09-28 | Se mantiene la atribución de React Flow (arriba a la derecha). | Ocultarla con `proOptions` | Solo corresponde con suscripción Pro. |
